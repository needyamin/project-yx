# Project YX — Technical QA Report

**Date:** 2026-09-25
**Scope:** Full-application engineering audit, debugging pass and production-QA cycle
**Baseline commit:** `4706643` ("latest fix") + uncommitted work-in-progress
**Verdict:** Not production-ready yet — see §10. The specific defects found and fixed
materially improve stability, but a set of unverified end-to-end guarantees
(§8, §9) still stands between this build and a release.

## 0. Method

Baseline was established **before any change**, per the priority order
(Correctness → Stability → Synchronization → Responsiveness → Performance →
Resource efficiency → Maintainability):

| Gate | Baseline | Final |
|---|---|---|
| `cargo test --workspace` | 77 passed, 0 failed, 2 ignored | **84 passed, 0 failed, 2 ignored** |
| `cargo check --workspace --all-targets` | 2 source warnings | **0 source warnings** |
| `npm run build` (tsc + vite) | green | green |

Findings were only acted on once the root cause was understood, and every fix
was re-verified against the full gate set. Where a suspicion could be measured
cheaply it was measured **before** being "fixed" — one candidate bottleneck was
investigated and deliberately left alone as a result (§7.1).

## 1–5. Issues discovered, severity, root cause, files, fixes

### D1 — Export can hang forever; cancellation is ineffective on a stalled encoder
**Severity: HIGH (stability / unrecoverable hang)**
**Root cause.** `run_ffmpeg_progress` drove its loop with
`for line in reader.lines().flatten()` directly on ffmpeg's stdout. Two
consequences:

1. Cancellation was only evaluated **when a progress line arrived**. A wedged
   encoder emits nothing, so the loop blocked in `read` forever and
   `cancel_export` had no effect on it.
2. `.flatten()` silently discarded read errors. If the reader stopped draining
   while ffmpeg kept writing, the OS pipe buffer filled, ffmpeg blocked on
   `write`, and the subsequent `child.wait()` blocked forever — a classic
   process-I/O deadlock.

There was no timeout anywhere in the path.
**Files.** `crates/yx-media/src/lib.rs` (`run_ffmpeg_progress`)
**Fix.** stdout is drained on a dedicated thread into an `mpsc` channel; the
main loop uses `recv_timeout(200 ms)`, polls the cancel flag **on every
iteration** (not only during silence), treats a stdout read error as fatal
(kill + report, never a silent EOF), and kills + reports after
`FFMPEG_STALL_TIMEOUT` (120 s of total silence) with ffmpeg's stderr attached.
The 120 s budget is deliberately generous: it only has to be shorter than
"forever" to convert an unrecoverable freeze into a reported error, and
`-progress pipe:1` is unconditionally injected by both callers, so legitimate
long encodes keep emitting.

### D2 — A running job could be started past the concurrency cap
**Severity: HIGH (resource exhaustion)**
**Root cause.** `JobManager.cancel()` deleted an *active* item from the
`active` set and immediately called `pump()`, freeing its slot while the job
was still running. Cancelling during a batch of thumbnail/ffmpeg jobs therefore
**raised** peak concurrent work instead of lowering it — the exact opposite of
the cap's purpose.
**Files.** `apps/desktop/src/jobs/jobManager.ts`
**Fix.** A running job keeps its slot until it actually settles; the abort
signal ends it promptly. Verified: peak concurrency is 3 on the old code, 2 on
the new (§6.2).

---

### D3 — A priority bump executed the same job twice
**Severity: HIGH (duplicate work — double ffmpeg/decode load)**
**Root cause.** On a more-urgent re-enqueue for an id already in flight,
`enqueue()` bumped `existing.priority` and then **fell through** to create a
*second* `QueueItem` for the same id and pushed it onto the queue. The original
item stayed queued, so both ran.
**Files.** `apps/desktop/src/jobs/jobManager.ts`
**Fix.** The bump mutates the existing item in place and returns it. `pump()`
re-sorts the queue each iteration, so promotion still takes effect. Verified:
`bg` ran twice before, once after.

---

### D4 — Coalesced job promises resolved before the work was done
**Severity: HIGH (correctness of the scheduler contract)**
**Root cause.** For a coalesced request the returned promise was
`Promise.resolve()` — i.e. it settled immediately. For a non-coalesced request
it was an unbounded 50 ms `setTimeout` polling chain.
**Files.** `apps/desktop/src/jobs/jobManager.ts`
**Fix.** Each item owns a real deferred `settled` promise, resolved in the
`finally` that already tracked completion (and on drop/abort). All `setTimeout`
polling is gone. The misleading always-`false` `cancelled` field was removed
from the return type.

---

### D5 — Blank timeline waveform on the second clip of a shared source
**Severity: MEDIUM (visible correctness)**
**Root cause.** A latent bug exposed by D4. `WaveformCanvas` did
`handle.promise.then(() => setReady(true))`. When two clips of the same file
mounted, the second coalesced onto the first's in-flight job, got an
immediately-resolved promise, set `ready = true`, and ran its draw effect while
`getCachedOverview(src)` was still `null` — the effect returned early. Because
`ready` never changes again and the effect's other deps are stable, the clip
stayed blank permanently. The `signalAborted(handle)` guard it relied on read a
field that was always `false`.
**Files.** `apps/desktop/src/timeline/WaveformCanvas.tsx`
**Fix.** Gate readiness on the data actually being cached
(`getCachedOverview(src)`) rather than on the job settling. The dead
`signalAborted` helper was removed.

---

### D6 — Import blocked the async runtime and fanned out without bound
**Severity: HIGH (responsiveness on low-end hardware)**
**Root cause.** Two independent problems in one command:

1. `cached_probe` (a blocking `ffprobe` subprocess) was called **directly
   inside an `async fn`**, so it blocked an async-runtime worker thread rather
   than the blocking pool. A batch import blocked one worker per file until
   every worker was stuck, stalling unrelated IPC (save, load, export) behind
   it. The function's own doc comment claimed it protected the UI thread.
2. Each import did `std::thread::spawn`, and each spawned thread called
   `ProxyManager::enqueue`, which runs **its own** `ffprobe`. Dropping a folder
   of 500 clips created 500 OS threads and up to 500 concurrent `ffprobe`
   processes — while the user is editing.

**Files.** `apps/desktop/src-tauri/src/lib.rs` (`import_media`)
**Fix.** The probe runs on `spawn_blocking`, with the in-memory `probe_cache`
checked first. Proxy enqueue goes through one long-lived dispatcher thread
(`proxy_enqueue_queue`) draining a channel, so the import path only performs a
channel send and proxy probe+transcode is serialized behind the manager's
single worker.

### D7 — A proxy job could wedge permanently in `Running`
**Severity: HIGH (permanent inconsistent state, no recovery)**
**Root cause.** `std::fs::rename(&tmp_path, &proxy_path)?` returned early on
failure, leaving the job in `Running` and the tmp file on disk.
`playback_path()` only serves `Ready | Skipped`, and `enqueue()` only retries
`Failed | Cancelled` — so a transient rename failure (disk full, AV lock, cache
dir removed) **permanently disabled proxies for that source** with no path back.
**Files.** `crates/yx-proxy/src/lib.rs` (`run_job`)
**Fix.** A rename failure now removes the tmp file, marks the job `Failed` with
the OS error, and returns `ProxyError::Io` — a state `enqueue()` can retry.

---

### D8 — Queued proxy jobs could not be cancelled
**Severity: MEDIUM (documented behaviour did not hold)**
**Root cause.** The cancel flag map is only populated once `run_job` starts. A
job still in `Queue` had no flag, so `cancel()` returned `false` and did
nothing — the transcode the caller just cancelled ran to completion. The doc
comment promised "queued/running".
**Files.** `crates/yx-proxy/src/lib.rs` (`cancel`, `run_job`)
**Fix.** `cancel()` registers a flag for a known-but-not-yet-started job;
`run_job` now *reuses* an existing flag (rather than replacing it with a fresh
`false` one, which silently discarded the request) and honours it before
spawning ffmpeg. Locks are taken one at a time so this cannot deadlock against
`run_job`'s acquisition order.

---

### D9 — Proxy cancel path leaked its flag; non-UTF-8 paths silently became `""`
**Severity: MEDIUM / LOW**
**Root cause.** (a) The in-loop cancel path returned before the shared cleanup
line, leaking one `cancels` entry per cancelled job. (b)
`source.to_str().unwrap_or_default()` substituted an **empty string** as
ffmpeg's `-i` argument on a non-UTF-8 path, so the user saw a confusing decoder
error instead of the real cause.
**Files.** `crates/yx-proxy/src/lib.rs`
**Fix.** (a) The flag is removed on the cancel path. (b) Non-UTF-8 source and
output paths now produce an explicit, actionable error.

---

### D10 — `probe_media` spawned two processes and reported failures as an empty string
**Severity: MEDIUM (performance + diagnosability)**
**Root cause.** `ensure_ffmpeg()` ran a full `ffmpeg -version` subprocess on
**every** probe (two processes per probe). Separately, ffprobe was invoked with
`-v quiet`, which guarantees `output.stderr` is empty — so every unreadable or
corrupt file produced the useless message `"ffprobe failed: "`.
**Files.** `crates/yx-media/src/lib.rs` (`ensure_ffmpeg`, `probe_media`)
**Fix.** The availability check is cached process-wide **on success only** (a
failure stays uncached, so a repaired install is picked up without a restart).
ffprobe now runs with `-v error`, with a status-based fallback if stderr is
still empty. Measured: **231.45 → 117.42 ms per probe (−49%)**, 2 processes → 1.

---

### D11 — No variable-frame-rate detection
**Severity: MEDIUM (model gap behind a class of sync bugs)**
**Root cause.** `probe_media` read only `avg_frame_rate` and had no notion of
VFR. VFR sources cannot be indexed by frame number, and the timeline maps
frames to time in several places.
**Files.** `crates/yx-media/src/lib.rs`, `apps/desktop/src/timeline/types.ts`
**Fix.** Added `MediaInfo.is_variable_frame_rate`, derived from the standard
ffprobe signal (nominal `r_frame_rate` vs `avg_frame_rate` disagreeing by more
than 0.5 fps), with a pure, unit-tested helper. Fractional CFR rates
(23.976/29.97/59.94) are explicitly **not** misclassified, and missing/zero
rates are never treated as VFR. **The UI does not act on this yet** — it is
informational groundwork (§9).

---

### D12 — Unbounded in-memory thumbnail caches
**Severity: MEDIUM (steady memory growth over a long session)**
**Root cause.** `cache: Map` and `failed: Set` in `thumbnails.ts` were keyed by
`(file, 0.25 s bucket)` and never evicted. One hour of media is ~14 400 keys.
**Files.** `apps/desktop/src/timeline/thumbnails.ts`
**Fix.** FIFO cap of 4000 entries on both. Safe in both directions: Rust keeps
the JPEG in its own on-disk cache, so a dropped URL re-resolves to a cheap disk
hit rather than a re-encode, and a dropped failure mark merely permits a later
retry.

---

### D13 — `clipEqual` could silently stop preserving memoization
**Severity: MEDIUM (maintainability; a landmine for future work)**
**Root cause.** `reconcileTimeline` reuses a clip's previous object reference
only if `clipEqual` reports it unchanged. The comparison lists fields
explicitly, so **adding a field to `Clip` without adding it there** would let a
real content change be treated as "unchanged" — the memoized `ClipBlock` would
keep painting stale content, with no error.
**Files.** `apps/desktop/src/timeline/reconcile.ts`
**Fix.** A zero-runtime-cost compile-time exhaustiveness assertion
(`CLIP_COMPARISON_IS_EXHAUSTIVE`). Verified by injecting a field: `tsc` fails
with `Type 'boolean' is not assignable to type '{ uncompared_clip_fields:
"opacity"; }'`.

---

### D14 — Two pre-existing compiler warnings
**Severity: LOW**
Unused `i` in a `yx-timeline` test; non-`snake_case` test name in
`yx-media/src/region.rs`. Both fixed; `cargo check --all-targets` is now
warning-free.

The `reconcile.ts` exhaustiveness assertion was proven to **fire**, not merely

### 6.4 Determinism

All new tests were run repeatedly. Two initially-flaky tests were rewritten
rather than tolerated: a 20 s export finished in <700 ms (so a sleep-based
cancel raced it) and a "silent ffmpeg" fixture finished inside its budget.
Both now use deterministic triggers — cancelling from inside the first progress
callback, and a workload (1080p `veryslow`, 60 s) that cannot finish inside the
budget. 3/3 and 2/2 consecutive green runs respectively.

No packaged-app run, no 4K/high-bitrate media, no 30/60-minute drift matrix, no
low-end-hardware acceptance pass, no real pointer/keyboard-driven end-to-end
UI session. The playback/clock fixes already present in the working tree
(`App.tsx`) were **reviewed but not modified** — see §8.

## 7. Performance measurements

### 7.1 Per-frame covering-set scan — investigated, measured, **not** changed

`commitPlayhead` runs on every playback frame and calls `updateUnderPlayhead`,
which calls `videoStackAtPlayhead` (filter + **sort**, allocating) plus
`clipAtPlayhead` twice and `secondAudioAt`. This appeared to contradict
invariant 3 ("the playback loop reads refs — no per-frame timeline scans") and
to be a prime "timeline gets slower as the project grows" suspect.

Measured with the **real** helpers from `timeline/types.ts`:

| Project | Clips | Cost/call | Cost/frame @60 fps |
|---|---|---|---|
| small 2V/2A × 25 | 100 | 0.49 µs | 0.029 ms |
| medium 3V/3A × 80 | 480 | 0.79 µs | 0.048 ms |
| large 4V/4A × 125 | 1000 | 1.32 µs | 0.079 ms |
| stress 6V/6A × 250 | **3000** | 3.15 µs | **0.189 ms (1.1% of budget)** |

**Conclusion: not a bottleneck.** The scan is linear with a very small
constant; even at 3000 clips it consumes ~1% of a 60 fps frame budget. The
invariant-3 comment is imprecise (the scan *does* happen per frame), but
"optimising" it would be speculative work against a non-problem. Left alone
deliberately; the comment should be corrected when someone next touches it.

### 7.2 `ensure_ffmpeg` process elimination (D10)

| | Before | After |
|---|---|---|
| Wall time per probe (20 probes, warm FS) | 231.45 ms | **117.42 ms** |
| Subprocesses per probe | 2 | 1 |
| `ffmpeg -version` alone | 113.92 ms | (cached, 0) |

A **−49%** reduction on the most frequent FFmpeg-touching operation in the app,
and it halves the process count during import and export.

### 7.3 Concurrency

- Job manager peak concurrency during cancel: **3 → 2** (cap honoured).
- Duplicate job executions on a priority bump: **2 → 1**.
- Proxy probe/transcode fan-out on a 500-file import: **≤500 threads + ≤500
  concurrent ffprobe → 1 dispatcher thread + serialized probes**.
- Import probe no longer occupies an async-runtime worker.

## 8. Remaining known issues

Reported, root-caused, **not fixed** in this pass — each needs either a
behavioural decision or a larger change than "the smallest robust fix".

| # | Issue | Severity | Why it was left |
|---|---|---|---|
| R1 | **No export mutual exclusion.** `export_cancel` is a single shared `AtomicBool` and `export_media` has no guard against concurrent runs, so a second export's `store(false)` un-cancels the first, and cancelling cancels both. | MEDIUM | Needs a UI/product decision (queue? reject?) plus a guard; the UI currently appears to serialise exports, so the race is not reachable from the normal path. |
| R2 | **`magic.rs` can silently produce a short/blank result.** `FrameReader::spawn` sets `stderr(Stdio::null())`, and `next_frame()` returns `Ok(false)` on early EOF **without checking the child's exit status** — a corrupt/partially-written source is indistinguishable from a clean end of stream. | MEDIUM | Fix is clear (keep stderr, verify status at EOF) but touches the Magic Remove render path, which has no cheap end-to-end test here. |
| R3 | **`ProxyManager::cancel` is unreachable.** No Tauri command and no UI path calls it; the capability is dead code. Proxies for deleted media keep encoding. | MEDIUM | Wiring it needs a product decision about *when* to cancel (clip delete? timeline clear?). The API itself is now correct for whoever wires it. |
| R4 | **`transitioningRef` 50 ms window.** Deliberate media pauses are suppressed by a hardcoded timer, not by an explicit cause token — a timing assumption the brief explicitly discourages. | MEDIUM | This is load-bearing for gap/cut playback and is documented as having been tuned against real bugs. Changing it without a reproduction of the original failure risks reintroducing "playback freezes at the first gap". |
| R5 | **Export `probe_media` in the non-timeline branch** still runs synchronously inside an `async fn`. | LOW | Same class as D6 but only on a cold path with no proxy fan-out. |
| R6 | **`waveformPeaks` `overviewCache`/`overviewFailed` remain unbounded** (one 16 KB entry per media file), unlike `decodedCache` which is capped at 24. | LOW | ~16 KB/file is small; capping needs the same care as D12. |
| R7 | **Pre-existing, unverified guarantees**: 30/60-minute drift matrix, low-end-hardware acceptance pass, packaged-WebView2 frame-pacing check (the 1080p60 ~78–92% presented-frame figure), seek-latency (~130 ms) and the decoded-frame-cache idea. | — | Already listed as open in `context_memory.txt` §7; they require the packaged app and real media on target machines, which this environment cannot provide. |

The uncommitted `App.tsx` / `ProjectMonitor.tsx` / `qa.ts` changes (playback

## 9. Recommended architectural improvements

Ordered by leverage.

1. **Give every long-running subprocess one lifecycle primitive.** Three
   separate hand-rolled implementations exist (`yx-media`'s `KillOnDrop` +
   progress loop, `yx-proxy`'s poll loop, `magic.rs`'s `FrameReader`), and each
   got a different subset of drain/timeout/cancel/exit-status handling right.
   One shared "supervised child" helper (kill-on-drop, drained pipes, deadline,
   cancel token, exit-status verification) would have prevented D1, R2 and most
   of D7 at the source.
2. **Adopt a single cancel/timeout convention** (`AtomicBool` + deadline) and
   apply it uniformly to export, proxy, magic and blur tracking. Today each has
   its own ad-hoc polling cadence.
3. **Introduce a frontend test runner** (Vitest is the natural fit with Vite
   8). The Node harness used here proved the modules are testable in isolation;
   a real runner would turn §6.2 from an ad-hoc script into CI.
4. **Correct invariant 3's wording** and add the measurement from §7.1 next to
   it, so the next engineer does not re-investigate the covering-set scan.
5. **Make `MediaInfo` VFR information actionable** (D11): when
   `is_variable_frame_rate` is set, surface it (import badge / status) and make
   sure every frame↔time mapping on that clip uses timestamps.
6. **Bound every cache with an explicit policy** and assert it. D12 fixed two;
   R6 remains; a tiny shared `BoundedMap` helper would make the policy visible
   at each call site.
7. **Serialise export explicitly** (R1) — a single `export_busy` guard plus a
   per-run cancel token, so two exports can never share one flag.
8. **Reduce `App.tsx` (5 280 lines)** — it is the single largest correctness
   risk in the codebase (app state, playback engine, keyboard, persistence and
   monitor sync in one component). Extracting the playback engine into its own
   module would make the sync logic unit-testable.

## 10. Production-readiness assessment

**Based on the tested evidence, this build is not yet production-ready — but it
is materially closer, and no defect fixed in this pass was left unverified.**

**What the evidence supports**

- The FFmpeg export path no longer has a known unbounded wait. The specific
  failure the brief calls out — *"FFmpeg process becomes stuck"* — is now
  converted into a reported error, verified against real ffmpeg.
- The background scheduler now enforces the concurrency cap it advertises, no
  longer duplicates work on promotion, and its completion contract is honest.
  Verified by a harness that **fails on the previous revision and passes on this
  one**.
- Import no longer blocks the async runtime, and the thread/process fan-out on a
  large drop is bounded by construction rather than by hope.
- Proxy jobs can no longer wedge in a state with no recovery path.
- The most frequent FFmpeg-adjacent operation is 49% cheaper and spawns half the
  processes.
- Every gate is green and warning-free, with 7 new regression tests including 4
  that drive a real ffmpeg.

**What the evidence does not support**

- **No end-to-end validation in the packaged app.** All Rust tests run in
  `cargo test`; the frontend harness runs in Node. Neither exercises the real
  WebView2 media pipeline, which is where the remaining playback risk lives.
- **The A/V synchronisation work is unverified.** It is in the working tree,
  it is plausibly correct, and it is **not** covered by any automated test here.
  The `/qa.html` harness exists precisely for this and must be run.
- **4K / high-bitrate / long-duration behaviour was not measured.** The brief's
  core product goal is 4K on low-end hardware; nothing in this pass produced
  evidence about it. The one relevant number available (0.19 ms/frame at 3000
  clips) bounds *timeline* cost, not decode or render cost.
- **R1–R4 are real, known, and unfixed.** None is a crash, but R2 can silently
  produce a wrong render and R1 is a latent correctness race.

**Recommended gate before release**

1. Run `/qa.html` with `?seed=speed`, `?seed=split`, `?seed=reverse`,
   `?seed=speedcut`, `?seed=reverse-overlap` in the packaged WebView2 window and
   confirm the documented regression classes stay fixed.
2. Execute the 30/60-minute drift matrix and the low-end-hardware acceptance
   pass with real 4K and high-bitrate media.
3. Fix R1 and R2 (both have clear, small fixes).
4. Add `npm run test:js` (and the new `export_progress_ffmpeg` suite) to the
   pre-commit gate and to CI, so the regressions proven here cannot silently
   return.

Until 1–2 are done, any statement about this editor's 4K playback and
long-session synchronisation would be an assumption, not a measurement — and the
brief is explicit that this is not acceptable.
